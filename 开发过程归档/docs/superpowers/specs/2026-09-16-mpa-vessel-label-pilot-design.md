# 马六甲 AIS 五分类 MPA 免费标签预检设计

日期：2026-09-16

## 1. 目标与范围

本阶段目标是验证新加坡海事与港务管理局（MPA）的 OCEANS-X / Singapore Maritime Data Hub 船舶资料接口，能否为现有马六甲海峡 AIS 船舶提供可追溯的细船型信息，重点补充：

- 集装箱船；
- 散货船；
- 油轮；
- 客船；
- 渔船。

本阶段只查询项目现有马六甲数据中的船舶，不采集其他海域 AIS，不重新采集轨迹，不启动 1,499 艘全量查询。先验证数据源价值，再决定是否扩量。

## 2. 已确认事实

- GFW 20 艘在线预检已实现 20/20 查询成功和 MMSI 对齐，但没有获得集装箱船或散货船标签，因此不能作为五分类唯一真值来源。
- MPA 官方船舶资料接口文档显示，可按 IMO、船名或呼号查询，并返回 `vesselType`、IMO、MMSI、船名、呼号、船旗、船长、船宽、船深、总吨、净吨、载重吨和建造年份；资料标称每 6 小时更新。
- MPA 的新加坡进出港申报要求提交 IMO、船型、吨位等船舶资料。项目采集范围覆盖新加坡海峡附近，因此该来源与本项目区域具有较高相关性，但实际覆盖率仍需实验验证。
- Equasis 可免费逐船查询，并包含较细船型；但其条款禁止批量下载、机器人和自动化定期提取，不能为其开发批量爬虫。仅允许研究人员按条款做少量人工交叉核验。
- Datalastic 的 Vessel Info 提供 `type_specific`、TEU、DWT 等字段，但属于付费服务。免费来源未验证失败前不购买。

## 3. 方案比较

### 方案 A：MPA 分阶段预检 + 少量人工核验（采用）

优点：官方来源、区域相关、字段较完整、具备 API 形式，适合后续可复现实验。风险是接口可能需要审批，且并非所有过境船都存在于 MPA 资料库。

### 方案 B：Equasis 人工逐船标注

优点：商船细分类较强。缺点是禁止自动化和批量下载，难以覆盖上千艘，只适合作为少量核验来源。

### 方案 C：Datalastic 付费补全

优点：API 成熟并直接提供船舶子类型。缺点是需要订阅，且购买前仍需确认马六甲样本覆盖率和标签质量。仅作为免费方案不足时的后备。

## 4. 两阶段预检

### 4.1 十艘技术预检

从现有 `vessel_query_manifest.csv` 选取 10 艘：

- 必须是有效 9 位 MMSI；
- 优先具有通过校验的唯一 IMO；
- 身份文本无冲突；
- 马六甲区域内有效轨迹点充足；
- 覆盖 AIS 粗类货船、油轮、客船及其他/未知类别。

技术预检验证：

- API Key 和接口权限；
- 请求是否按 IMO 返回结果；
- 是否包含船型及关键静态字段；
- 原始响应能否缓存；
- IMO、MMSI和船名能否与本地身份对齐；
- 失败、限流、无结果和字段缺失能否被区分记录。

10 艘没有通过技术门槛时立即停止，不进入 50 艘预检。

### 4.2 五十艘分类能力预检

技术预检通过后，使用固定分层样本：

- AIS 粗类货船：25 艘；
- AIS 粗类油轮：15 艘；
- AIS 粗类客船：5 艘；
- 渔船、其他或未知：合计 5 艘。

样本必须来自现有马六甲清单。优先使用有效 IMO；不通过船名猜测集装箱船或散货船，以免在抽样阶段引入标签泄漏。

## 5. 数据流与产物

1. 从阶段一逐船清单生成固定预检样本。
2. API Key 通过终端隐藏输入并仅放入子进程环境变量，不写入代码、CSV、日志或 Markdown。
3. 每个请求保存独立原始 JSON，文件名使用查询类型和标识符。
4. 请求状态单独保存，包含 HTTP 状态、尝试次数、缓存命中、时间和错误类型。
5. 来源感知审计器生成逐船证据表和汇总报告。
6. 只有通过身份对齐和船型映射规则的记录才能进入候选标签表。

建议目录：

- `源代码/船舶分类数据准备/mpa_vessel_enrichment.py`
- `源代码/船舶分类数据准备/audit_mpa_pilot.py`
- `源代码/船舶分类数据准备/启动MPA船型补全预检.ps1`
- `运行结果/MPA船型补全预检_2026-09-16/`

## 6. 标签和证据规则

MPA 原始 `vesselType` 必须原样保存，并使用独立映射字段生成五分类候选：

- 明确的 `Container Ship` 才映射为 `container`；
- 明确的 `Bulk Carrier` 才映射为 `bulk`；
- 明确的原油、成品油、化学品、液化气等 tanker 类型映射为 `tanker`，同时保留原子类型；
- 明确的 passenger/ferry 类型映射为 `passenger`；
- 明确的 fishing 类型映射为 `fishing`；
- `Cargo`、`General Cargo`、`Other`、`Unknown`、服务船和工程船均不强制映射为五分类。

身份规则：

- IMO 精确一致，且 MMSI 或标准化船名一致：可列为高可信候选；
- IMO 一致但 MMSI 和船名不一致：进入人工复核；
- 仅船名相似或返回多条冲突记录：进入人工复核；
- 无精确身份对齐：不得生成标签。

MPA 标签仍属于外部来源候选。抽取至少 10 艘，通过 IMO GISIS 或 Equasis 人工交叉核验后，才决定能否写入训练用真值表。

## 7. 验收和停止门槛

### 十艘技术预检门槛

- 接口成功返回率不低于 70%；
- 成功响应中的身份对齐率不低于 90%；
- 成功响应中的 `vesselType` 非空率不低于 80%；
- 原始响应、状态和错误均可追溯；
- Token 未出现在任何持久化文件中。

任何认证、许可或接口版本问题必须先解决，不允许绕过后继续批量请求。

### 五十艘分类能力门槛

- 成功返回率不低于 70%；
- 成功响应中的身份对齐率不低于 95%；
- 成功响应中的细船型覆盖率不低于 80%；
- 实际获得集装箱、散货和油轮类别，而不是只有宽泛 `Cargo` 或 `Other`；
- 人工核验样本不得出现系统性类别冲突。

如果没有同时获得集装箱、散货和油轮细分类，停止扩展到全量，并转向 Datalastic 小额试用或其他经许可的数据源。

## 8. 测试与错误处理

- 单元测试覆盖样本选择、IMO/MMSI匹配、船名标准化、船型映射、冲突处理和 Token 不落盘。
- 接口测试区分认证失败、权限不足、限流、服务器错误、网络错误、无结果和解析错误。
- 已成功响应必须缓存；重跑时只请求失败或缺失项。
- 429 和 5xx 使用有限次数退避重试；401/403 立即停止。
- 结果报告明确区分“API 成功”“身份对齐”“获得细船型”和“可作为候选标签”，不得混为一个成功率。
