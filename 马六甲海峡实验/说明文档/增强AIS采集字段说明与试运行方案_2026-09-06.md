# 增强 AIS 采集字段说明与试运行方案

日期：2026-09-06。状态：采集脚本方案与字段说明，尚未执行新采集。

## 一、为什么要新增增强采集

当前六小时分类基线说明，船舶分类准确度不佳不能只靠换模型解决。主要风险来自：短时 AIS 静态字段缺失、未覆盖 Class B 相关消息、标签未外部核验，以及轨迹特征受航行/低速/停泊状态混杂影响。

因此新增 `源代码/数据采集代码/采集马六甲AIS数据_增强消息版.py`，保留旧脚本不动。增强版的目标是尽量完整保存 AISStream 发来的分类相关字段，并保留原始 JSON，避免后续发现必要字段没有落表。

## 二、增强版默认订阅消息类型

默认订阅：

```text
PositionReport
ShipStaticData
StandardClassBPositionReport
ExtendedClassBPositionReport
StaticDataReport
```

这些消息类型来自 AISStream 官方文档的支持列表。其中 `PositionReport` 主要对应 Class A 动态位置，`ShipStaticData` 对应 Class A 静态与航次资料，`StandardClassBPositionReport` 和 `ExtendedClassBPositionReport` 对应 Class B 动态位置，`StaticDataReport` 对应 Class B 静态资料。

## 三、字段分组

### 1. 轨迹与动态字段

用于轨迹切段、行为特征、分类模型和异常检测：

```text
mmsi
message_type
received_at
metadata_time_utc
ais_timestamp
lat
lon
sog
cog
true_heading
rate_of_turn
navigational_status
position_accuracy
raim
special_manoeuvre_indicator
communication_state
assigned_mode
dte
```

### 2. 静态、船型和几何字段

用于船型标签、船体几何特征和外部核验：

```text
vessel_name
call_sign
imo
vessel_type
ais_version
fix_type
destination
eta_month
eta_day
eta_hour
eta_minute
draught
dimension_to_bow
dimension_to_stern
dimension_to_port
dimension_to_starboard
ship_length
ship_width
vendor_id_name
vendor_id_model
vendor_id_serial
```

`ship_length` 由 `dimension_to_bow + dimension_to_stern` 得到，`ship_width` 由 `dimension_to_port + dimension_to_starboard` 得到。若原始消息未提供尺寸字段，则留空，不推断。

### 3. 复现与追责字段

用于确认采集版本、范围、解析质量和字段追溯：

```text
collector_version
source
bbox
parse_status
parse_error
raw_json
```

`raw_json` 默认保存。正式字段覆盖测试时不建议关闭，因为它能在解析逻辑需要补充时保留原始证据。

## 四、能否保证采集到必要字段

不能保证每艘船都采到完整字段。原因是 AIS 是事件驱动流，静态资料不是每条位置消息都带，且 AISStream 官方文档说明消息接收会受过滤、船舶活动、上游中断、网络和客户端消费速度影响，也不提供历史回放和 SLA。

增强脚本能保证的是：只要 AISStream 发来的消息里有这些字段，就尽量展开保存；如果暂时没有展开到 CSV，也会在 `raw_json` 中保留，便于后续补解析。

## 五、建议采集多久

不建议一开始长时间采集。建议三步走：

1. 字段覆盖试运行：30 分钟。目标是确认是否收到 Class B、StaticDataReport、船长船宽、船型、导航状态等字段。
2. 六小时对照采集：如果 30 分钟字段覆盖正常，再采 6 小时，与旧六小时数据对比未知比例、静态字段覆盖率、Class B 覆盖和候选样本数。
3. 多日正式数据：如果六小时对照有效，再采 3 个独立时间段，每次 6-12 小时，分别作为开发集、验证集和封存测试集候选。封存测试集不能反复调参。

如果 30 分钟试运行显示字段覆盖仍然很差，应及时转向外部历史 AIS 数据、商业/申请数据或人工核验方案，不继续盲目实时采集。

## 六、推荐运行方式：沿用历史成功环境

参照 `说明文档/AIS数据采集操作流程.md`，本项目优先沿用历史成功的 Codex 自带 Python 和旧项目依赖目录，不依赖系统 `python` 命令。打开 PowerShell 后执行：


启动器会自动检查：


若当前窗口还没有 `AISSTREAM_API_KEY`，会用隐藏输入提示你粘贴 Key。不要把 API Key 写进截图或文档。

增强脚本默认 `--print-every 1`、`--flush-every 1`，即每采到一行就在终端显示一行摘要，并立刻刷新写入 CSV。若暂时没有收到消息，会每 30 秒输出一次等待状态。若后续长时间采集嫌刷屏，可以改成每 100 行显示和刷新一次：

```powershell

  -PrintEvery 100 `
  -FlushEvery 100
```

启动器会为每次采集自动生成新的时间戳文件名，直接保存到 `桌面\马六甲海峡实验\原始数据`，并在采集结束后自动运行字段覆盖检查。若要手动检查，也可以用下面命令：


重点看 `message_type` 分布、`vessel_type`、`vessel_name`、`ship_length`、`ship_width`、`navigational_status`、`true_heading`、`raw_json` 的覆盖率。若船型和尺寸字段几乎没有覆盖，不建议直接长时间采集，应先调整数据源或核验路线。

若系统 `python --version` 提示没有 Python，不影响上述启动器；它使用的是历史成功的 Codex 自带 Python。若启动器检查 `websockets` 失败，再按 `AIS数据采集操作流程.md` 中的依赖修复方法处理。
